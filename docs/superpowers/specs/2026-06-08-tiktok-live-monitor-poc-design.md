# TikTok Live Monitor — Standalone Proof-of-Concept Design

**Date:** 2026-06-08
**Status:** Approved (brainstorm) — ready for implementation plan
**Scope:** A throwaway-harness / keep-the-core standalone Electron app that proves the TikTok Shop live data plane end-to-end before any integration into `sellerfolio-platform`.
**Companion:** `docs/superpowers/specs/2026-06-08-tiktok-live-traffic-capture.md` (the capture findings this design is built on).

## Why a PoC first

The uncertainty in a TikTok Live Monitor is **not** in the UI or the platform plumbing — it's in the data plane. The integration (Prisma, multi-tenant auth, the redesigned `LiveMonitor.tsx`, the `LiveSource` refactor that touches the live-show-critical Whatnot path) is real cost we should not pay before the foundation is proven. The PoC isolates and validates the four genuinely unproven things:

1. **Capture stability** — does the in-page `XMLHttpRequest` hook stay live and authenticated across a *full* show (hours), not just a 4-minute probe?
2. **Decode durability** — does the schemaless protobuf walker hold across every event variant over time, or does it drift?
3. **Sale dedup correctness** — is the stream↔roster sale reconciliation correct against ground truth (the dashboard's own `num_sold`)?
4. **Connection lifecycle** — room/session auto-detection, reconnect after reload, logged-out handling.

## Design philosophy: throwaway harness, portable core

The PoC is structured so the **valuable part is not throwaway**. A thin Electron harness wraps a portable core module. The harness is disposable; the core ports directly into the eventual desktop `TikTokLiveSource` with its unit tests intact.

```
┌─────────────────────────── PoC (disposable) ───────────────────────────┐
│  Electron main:  hidden/visible BrowserWindow → streamer dashboard      │
│  preload:        XMLHttpRequest hook → forwards raw im/fetch bytes       │
│                  + raw added_auction_product/list JSON over IPC          │
│  renderer:       minimal live view (current auction, bid ticker,         │
│                  sales feed, sold/failed counts) + validation panel      │
└──────────────────────────────────┬──────────────────────────────────────┘
                                    │ raw bytes / raw JSON
┌──────────────────────────────────▼─── core/ (PORTABLE, keep) ───────────┐
│  decoder.ts      protobuf wire-walker  → field tree                      │
│  mapper.ts       field paths           → normalized stream events         │
│  rosterDiffer.ts roster JSON snapshots → state + derived sales + dedup    │
│  normalizer.ts   merges stream + roster → one ordered LiveEvent stream    │
│  types.ts        the normalized event model (shared contract)             │
└───────────────────────────────────────────────────────────────────────┘
```

`core/` has **zero Electron / DOM / framework dependencies** — pure functions over bytes and JSON, so it is unit-testable in plain Node and drops into the desktop app unchanged.

## Normalized event model (the contract)

This is the same contract the production `LiveSource` will expose, so the core is written against it from day one.

```ts
type Money = { cents: number; formatted: string }            // {3100, "$31.00"}
type Buyer = { username: string; displayName?: string; avatarUrl?: string }
type ProductRef = { auctionConfigId: string; productId?: string; skuId?: string;
                    name: string; variantDesc?: string; imageUrl?: string }

type AuctionEvent = { kind: 'auction_started' | 'auction_ended';
                      product: ProductRef; price?: Money; ts: number }
type BidEvent    = { kind: 'bid'; auctionConfigId: string; price: Money;
                     bidCount: number; bidder?: Buyer; ts: number }
type SaleEvent   = { kind: 'sale'; status: 'sold' | 'payment_failed';
                     product: ProductRef; price: Money; buyer?: Buyer;
                     dedupeKey: string; source: 'stream' | 'roster'; ts: number }
type StateSnapshot = { kind: 'state'; pinnedAuction?: AuctionState;
                       products: AuctionState[]; totals: { sold: number; failed: number };
                       ts: number }
type StatusEvent = { kind: 'status';
                     status: 'connecting' | 'connected' | 'idle' | 'needs-login' | 'error';
                     detail?: string }

type LiveEvent = AuctionEvent | BidEvent | SaleEvent | StateSnapshot | StatusEvent
```

## Authentication & session

**Principle: ride a persisted, interactively-authenticated browser session. Never replicate TikTok's auth or request signing.**

Every TikTok request observed in capture is signed per-request with `msToken` + `X-Bogus` + `X-Gnarly`, generated by ByteDance's obfuscated `webmssdk_ex.js` + the `mssdk` device SDK (rotating `msToken`, device fingerprint `fp`/`ttwid`/`odin_tt`, plus an `oec-captcha` challenge SDK). Stored cookies alone are therefore insufficient and headless cookie-replay gets rejected/captcha-walled. The signing must come from a real browser context.

### Login (interactive, user-driven)
- Open TikTok's real login page in an Electron `BrowserWindow`; the **user authenticates themselves** (email/SMS/QR/SSO, 2FA, and solves any captcha).
- The PoC/app **never enters credentials and never solves captchas** on the user's behalf (hard rule; headless would hit the captcha wall regardless).

### Session persistence
- Use a **persistent Electron partition** (`persist:tiktok-<sellerId>` in the real app; a single `persist:tiktok` for the PoC). Cookies survive restarts; TikTok sessions are long-lived, so login is occasional, not per-run.
- Core session cookies (`sessionid`, `sid_tt`, `sid_guard`, `uid_tt`, `ttwid`, `msToken`) are largely **httpOnly** — they live in the Electron session store. We do **not** extract them; the window uses them in place.
- Keep **one stable partition per seller** (a stable "device"); rotating partitions/fingerprints trips TikTok risk controls.

### Multi-domain SSO
Auth spans `shop.tiktok.com`, `seller-us.tiktok.com`, `livecenter.tiktok.com`, `webcast.us.tiktok.com`. One login lights up the others via SSO, but `seller-us` and `livecenter` each need a first visit to set their domain cookies — so the connect flow visits each surface once in the same partition.

### Data access within the session
Run **from a real TikTok page** (so the signing SDK is loaded), then either: (a) the in-page XHR/fetch hook reads responses the page itself signs, or (b) page-context `fetch` pulls chosen endpoints (the page SDK signs them — as proven by replaying `trade/orders/get` during capture).

### Re-auth handling
Detect `401` / redirect-to-login → emit `status: needs-login` and reopen the login window. Same status-event contract the live event sources already expose.

### Multi-tenant (real app, not PoC)
Desktop-only (web app can't hold a browser session — consistent with the CLAUDE.md rule that live-monitoring stays Electron IPC). One persisted partition **per seller/TikTok account**; cookies stay **on the desktop machine**, never synced to the DB. Server-side stores only a "connected / last-seen" flag.

### Empirical finding (2026-06-08 live test) — embedded fresh login does NOT work for TikTok

Tested the PoC's embedded-login against TikTok Seller Center (`seller-us.tiktok.com`) on Windows. **A fresh interactive login inside the embedded Electron browser consistently fails** — `error_code 1042 "Ticket expired"` and generic TikTok error pages — despite all of:
- a real Chrome-on-Windows User-Agent (not the default `Electron/…`),
- login popups allowed and scoped to TikTok origins,
- a clean persisted partition (cleared between attempts),
- correct system clock,
- QR-code login as well.

Root cause: TikTok's passport/anti-bot + device verification (`webmssdk`/`mssdk`, device fingerprint) rejects a fresh login from a blank-profile embedded Chromium. By contrast, the user's **established real Chrome on the same machine is authenticated and the full capture + decode works there** (demonstrated earlier in this session).

**Decision — for TikTok, do NOT rely on fresh embedded login. Reuse an existing authenticated browser session.** Production options:
- **(a) Browser extension** in the user's real Chrome (hooks `im/fetch`/roster in-page, posts normalized events to the app), or
- **(b) CDP attach** to the user's running Chrome.

Copying Chrome cookies into an Electron partition is impractical (Chrome App-Bound Encryption) and crosses a credential boundary — rejected.

**Implication vs. Whatnot:** the Whatnot monitor's embedded-login pattern works; **TikTok does not follow it** and needs the real-browser-session approach. This does not affect the portable `core/` (decoder/mapper/rosterDiffer/normalizer) at all — it consumes the same normalized events regardless of where the raw frames are hooked. Only the *harness/transport* changes from "embedded window with its own login" to "extension/CDP hook on the existing session."

## Data flow

1. **Connect:** Electron opens a `BrowserWindow` on `shop.tiktok.com/streamer/live/event/dashboard` using the user's existing Chrome/TikTok session. Preload injects the XHR hook before page scripts.
2. **Room detection:** read `room_id` from the first `im/fetch` request (or `live_session/get`). Emit `status: connected` once a room is seen; `idle` if no active live; `needs-login` if redirected to auth.
3. **Stream path:** preload forwards each `im/fetch` arraybuffer to `core/decoder` → `core/mapper` → `AuctionEvent`/`BidEvent`/`SaleEvent`.
4. **Roster path:** preload forwards each `added_auction_product/list` JSON to `core/rosterDiffer` → `StateSnapshot` (+ derived `SaleEvent`s from `num_sold`/`win_username` deltas).
5. **Merge:** `core/normalizer` reconciles both into one ordered `LiveEvent` stream (see dedup below) and hands it to the renderer.

## Sale detection & dedup

TikTok has no single clean "sale" event. A sale = an auction item that ended with a winner, signalled by **both** the stream (`auction.end` / `auction.result_update`) and the roster (`win_username` set + `num_sold` increment).

- **Dedupe key** = `auctionConfigId` + auction-item identity (`auction_bid_timestamp` / end-time bucket).
- **Fast path:** the stream emits the `SaleEvent` immediately on `auction.result_update` (`order_payment_time` present) or `auction.end`.
- **Authority:** the roster's per-product `num_sold` is the source of truth for counts. `rosterDiffer` emits a `SaleEvent` for any completed item the stream missed, and the validation panel flags any count mismatch.
- **Payment failure:** `auction.payment_failure` (stream) and `num_auction_payment_failed` (roster) → `SaleEvent{status:'payment_failed'}`, same dedup.
- **Degradation:** if the decoder is disabled/broken, sales are still detected from roster deltas alone.

## Minimal UI

A single window, three panes, intentionally unstyled beyond legibility:
- **Now:** current/pinned auction — product, image, current bid, bid count, time left.
- **Feed:** reverse-chronological `BidEvent`/`SaleEvent`/`AuctionEvent` ticker.
- **Totals + Validation:** sold/failed counts, and a live diff of *our derived* sold count vs the roster's `num_sold` — the PoC's primary success metric.

## Validation (PoC success criteria)

- Run an entire live show; capture stays connected with no manual re-auth.
- Decoder: 0 unhandled event variants logged, or any new variant captured as a fixture (not a crash).
- **Derived sold/failed counts match the dashboard's `num_sold`/`num_failed` within the show, with 0 net dedup drift.**
- Reconnect (reload mid-show) recovers current state from the next roster poll.

## In / Out of scope

**In:** Electron harness, XHR hook, protobuf decode+map, roster poll+diff, sale dedup, minimal live UI, decode/dedup validation logging.

**Out (deferred to integration spec):** DB/persistence, multi-tenant + auth, the redesigned `LiveMonitor` UI, the Whatnot `LiveSource` refactor, show-level GMV/viewer stats (`room/info`), reporting, order/earnings reconciliation, video/replay capture.

## Testing

The 2026-06-08 capture provides **real fixtures**: actual `im/fetch` protobuf frames covering `auction.start/new_bid/end/result_update/payment_failure`, plus `added_auction_product/list` snapshots. Unit tests:
- `decoder` — bytes → expected field tree.
- `mapper` — each captured frame → expected normalized event.
- `rosterDiffer` — snapshot sequence → expected `StateSnapshot` + derived sales.
- `normalizer` — stream+roster interleavings → correct dedup (no double-count, no miss).

## Carryover to integration (the non-throwaway part)

`core/` becomes the internals of `desktop/src/lib/liveSource/TikTokLiveSource.ts`. The normalized event model becomes the shared `LiveSource` contract that `WhatnotLiveSource` also implements. Only the harness (Electron window mgmt + scratch renderer) is discarded.

## Open follow-ons (separate investigation, not PoC-blocking)

- **Orders / earnings / video — investigated, see capture doc §10–11.** Order list+detail, settlement statements, per-order HLS "video receipt", per-show HLS replay, and LIVE Center per-show analytics are all confirmed pullable from the authenticated session. This is a **separate track** (reporting/reconciliation + media archival) from the live-monitor PoC.
- **DECISION — official API vs. browser-session for the orders track.** TikTok Shop has an official **Partner/Open API** (OAuth-authorized shop: Orders, Fulfillment, Finance/Settlement) that is sanctioned and far more stable than scraping Seller Center. The **live-auction real-time stream, video receipts, and replay video have no official API** and require the browser-session approach. Recommended shape is a **hybrid**: official API for order/earnings data, browser-session capture only for the live + video pieces. Confirm current Open API scope before committing the orders track.
- Show-level GMV/viewers via `insights/workbench/live/detail/room/info`.
- Non-auction "Buy Now" shop sales (this show was auction-only).
